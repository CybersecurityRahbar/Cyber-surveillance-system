# تحويل الهاتف إلى كاميرا مراقبة وبثه إلى النظام

**الحالة الحالية:** أضيف نموذج أولي لتطبيق Android يستخدم CameraX ويرسل إطارات JPEG عبر WebSocket محمي بمفتاح API، مع معاينة مرئية وزري بدء/إيقاف وحد إرسال مستهدف يقارب 10 FPS. هذا نموذج أولي ولم يُختبر على هاتف فعلي بعد. أما البنية التالية الموصى بها (H.264 + WebRTC/WHIP + MediaMTX) فهي تطوير مستقبلي وليست المسار الذي يشغله التطبيق الحالي.

## البنية الموصى بها

بدلاً من أن يحاول الخادم الاتصال بعنوان IP الهاتف مباشرة، الأفضل أن يبادر الهاتف بإرسال الفيديو إلى بوابة وسائط مستقرة، ثم يقرأ محرك Python الفيديو من البوابة:

~~~text
Android CameraX
      |
MediaCodec (H.264 hardware encode)
      |
WebRTC publisher / WHIP
      |
MediaMTX media gateway
      |
RTSP internal stream
      |
Python / PyAV analysis worker
      |
Detection + Tracking + Traffic analytics
      |
Event storage + Control Room
~~~

## لماذا MediaMTX؟

MediaMTX خادم وسائط مفتوح وخفيف، وليس محرك رؤية حاسوبية. يدعم استقبال/نشر وقراءة مصادر الفيديو عبر WebRTC وRTSP وSRT وRTMP وHLS وMedia-over-QUIC، ويمكنه تحويل البروتوكول بين الناشر والقارئ.

التقسيم:
- الهاتف ينشر إلى مسار اسمه phone-road-01 عبر WebRTC/WHIP.
- MediaMTX يستقبل الفيديو ويدير الجلسة.
- محرك Python يسحب المسار داخلياً عبر RTSP.
- واجهة الويب يمكنها قراءة WebRTC مباشرة لاحقاً، ولا نمرر كل إطار فيديو عبر JSON أو FastAPI.

## اختيار البروتوكول حسب الشبكة

| السيناريو | البروتوكول | السبب |
|---|---|---|
| الهاتف والخادم على Wi-Fi واحد | HTTPS/WSS موثوق حالياً في تطبيق MVP؛ WebRTC/RTSP LAN تطوير لاحق | إعداد محلي يتطلب TLS وشهادة يثق بها الهاتف؛ لا نفترض أن HTTP/WS العادي يعمل مع إعداد cleartext الحالي |
| الهاتف يبث عبر الإنترنت | WebRTC + STUN، وTURN عند الحاجة | ICE يحاول تكوين المسار؛ TURN يرحل الوسائط إن لم ينجح الاتصال المباشر بسبب NAT |
| شبكة ضعيفة أو فقد حزم | SRT كخيار بديل | يحتوي على retransmission والتحقق من سلامة النقل |
| كاميرا IP جاهزة | RTSP | تستعمل واجهة البث الموجودة في الكاميرا |

**الاختيار الأول للتطبيق:** CameraX + MediaCodec H.264 + WebRTC/WHIP إلى MediaMTX. لا نحتاج أن نكتب بروتوكول الفيديو من الصفر.

## الاتصال عبر الإنترنت

الخيار المفضل لمشروع شخصي أو عدة مواقع هو VPN خاص بين الهاتف والخادم مثل WireGuard. عندما يلزم الوصول من الإنترنت العام دون VPN:
- استخدم HTTPS/TLS لإشارة WebRTC وواجهات الإدارة.
- استخدم مصادقة نشر منفصلة لكل كاميرا ومسار.
- جهّز STUN وخادم TURN موثوقاً عند الحاجة.
- لا تضع بيانات الاعتماد في URL أو سجلات التطبيق.
- لا تفتح RTSP أو منفذ كاميرا الهاتف للعامة.
- ألغِ credentials عند فقد الهاتف أو استبداله.
- افصل صلاحية نشر الفيديو عن صلاحية مشاهدته أو إدارته.

## إعدادات الفيديو الأولية

- H.264/AVC بسبب التوافق الجيد.
- ابدأ بـ 720p أو 1080p حسب الشبكة والمعالج.
- ابدأ بـ 15–25 FPS ثم قِس تأثير FPS على التتبع والـ latency.
- حافظ على PTS ووقت التقاط الإطار إذا كان المصدر يتيحه.
- أرسل metadata لهوية الكاميرا والدقة ومعدل الإطارات وحالة الشبكة.
- غيّر bitrate/FPS عند ضعف الشبكة وأظهر هذا التغيير في Camera Health.

## ما سنبنيه في تطبيق Android لاحقاً بعد نموذج WebSocket الأولي

1. واجهة واضحة لاختيار الكاميرا الخلفية/الأمامية.
2. CameraX للالتقاط مع ضبط الاتجاه والدوران.
3. MediaCodec H.264 hardware encoder.
4. WebRTC publisher يدعم WHIP وICE/STUN/TURN.
5. تسجيل اسم الكاميرا ومسار البث وبيانات الاعتماد الآمنة.
6. عرض bitrate وFPS وlatency وdropped frames وحالة الشبكة.
7. إعادة اتصال آمنة بعد انقطاع Wi-Fi أو تبديل الشبكة.
8. Foreground service بإشعار ظاهر أثناء البث مع زر إيقاف واضح.

التطبيق لن يبدأ التصوير خفية أو دون موافقة المستخدم، وسيعرض حالة البث دائماً.

## اختبار مسار وسائط H.264 المستقبلي قبل اعتماده

يمكن استخدام OBS أو FFmpeg كناشر تجريبي:
1. شغّل MediaMTX على جهاز الخادم.
2. انشر فيديو تجريبياً إلى MediaMTX عبر بروتوكول متاح.
3. تحقق من إمكانية قراءة المسار داخلياً عبر RTSP.
4. أدخل عنوان RTSP الناتج في المختبر.
5. راقب الكشف والتتبع وFPS والـ dropped frames قبل اختبار هاتف Android.

بهذا نفصل مشاكل الشبكة والبث عن مشاكل الرؤية الحاسوبية، ونستطيع إثبات مسار المعالجة قبل إضافة تطبيق الهاتف.
